-- что делает 'css-loader' :

- он умеет читать css,

--- НО он не занимается иньекцией стилей в наш ДОМ

- все что он делает - корректно обрабатывает CSS-код и кладет его прямо внутрь JS в виде строк

это можем увидеть так например в App.js:


import appStyles from './App.css';

console.log(appStyles);

- и видим что там массив, и в нем в одном из элементов есть нужные стили в виде строки 


---- А нам нужно, чтобы эти стили попали в тег <style>

---- для этого нам нужен еще лоадер для css

прошлый лоадер никуда не убираем,

тут мы приходим к концепции ЧЕЙНИНГА лоадеров:

когда к файлам css нужно применять не один, а несколько лоадеров (записываем через запятую)


  module: {
    rules: [{
      test: /\.js$/,
      use: 'babel-loader',
      exclude: /node_modules/
    }, {
      test: /\.css$/,
      use: ['style-loader', 'css-loader']
    }]
  }


--- когда вебпак видит что для какого-то типа файлов нужно применять несколько модулей, он делает т.н. ПАЙПЛАЙН

то есть он сначала применяет последний в списке, затем результат последнего передает предыдущему перед ним

- сначала 'css-loader' , затем 'style-loader'

- так содержимое файлов проходит через "трубопровод"

таким образом мы можем создавать цепочки трансформации

    }, {
      test: /\.css$/,
      use: ['style-loader', 'css-loader']
    }, {
      test: /\.svg$/,
      type: 'asset/resource'
    }]
  }


-- пересобираем, картинка выводится, все ок





-- ЧТО ТАКОЕ  'asset/resource'  ??

- это специальный тип, кот нам провайдит сам Вебпак

- он полезен тогда, когда мы помимо того что мы загружаем наш модуль бандл, нам еще нужно чтобы произошел ЕМИТ -  выплевывание какого-то файла в папку с нашей сборкой 

- картинки - как раз под такой тип статики подходят

- это просто файлы , на кот нам нужно сослаться

то есть:

- нам нужно правильный урл на этот ресурс,
- и чтобы вебпак положил этот файл в папочку дист самостоятельно
- мы не хотим вручную переносить его в папку дист

таким образом мы гарантируем, что в папке "дист", куда будет смотреть наш сервер, - будет все что нам нужно 

то есть все ресурсы автоматически туда положатся, нам не нужно будет делать руками



---- 
если вывести в консоль эту пер

import logo from '../../images/logo.svg'

console.log(logo);

---- увидвим путь до файла:

http://localhost:5500/dist/4e7ca289124645b42e68.svg


- причем имя файла исказилось




------------------------ - ПОЧЕМУ так??



- тут вебпак учитывает еще дин ньюанс веба - 


ресурсы могут быть закэшированы 

если зайти на вкладку Нетворк в браузере и перезагрузить страницу, 
 то можно увидеть, что некоторые ресурсы при подгрузке не загружаются снова (0 мс время загрузки в столбце соотв),
- а берутся из кэша


 - потому что браузер, ориентируясь на спец. заголовки, может при скачивании ресурсов, сохранять их к себе (на разных уровнях)

 и после, когда он видит чт обращение идет по тому жу урлу, и по этому урлу уже что-то хранится в его кэше, 
то он возьмет это из кэша 

для экономии времени

- это очень МОЩНЫЙ инструмент, 

кот есть во всех браузерах, которым обильно пользуются все разработчики, 

и сОДНОЙ стороны - это крутая технология, 

с ДРУГОЙ - если например мы заменим картинку в проекте (нам дизайнер перерисовал) , зальем на сервер

- то у большинства пользователей отобразится старая при загрузке сайта

-- потому что она ЗАКЭШИРОВАНА - урл то не поменялся..


---------- и вебпак за нас пытается решить эту проблему - 

- он генерит спец. строку, которой заменяет имя файла

эта строка всегда будет отражать содержимое файла - она изменится только когда этот файл изменится. (при других изменениях в проекте она не изменится)

- таким образом, мы каждый раз при изменении файла провоцируем браузер загрузить новую версию файла (так же произойдет и у поьзователей)



----- ИТАК, - с картинками все классно с кэшем.


НО, если мы заглянем в деерво страницы - увидим что наш скрипт не переименовывается  - он постоянно "main.js" - как мы задали

<script type="module" src="./dist/main.js"></script>

- такое поведение по умолчанию приведет к тому, что main.js закэшируется , и когда мы его обновим - у пользователей он обновится НЕ сразу

---------------------


такое поведение - когда у части пользователей файл не обновится, пока они не почистят у себя кэш руками или не сбросят его полностью, 

-- может приводить к СЕрьезным ПРОБЛЕМАМ

например вы зарелизили плохой код, поняли это и хотите исправить , залить обновленный  - и чтобы он был доступен обнолвен всем пользователям  

---- КАК это сделать?


- если мы в индексе просто будем ссылаться на имя файла - то мы не сможем этого достичь

<script type="module" src="./dist/main.js"></script>

- что делаем::

идем в конфиг вебпака,

и в "output" дописываем инструкцию, как должно меняться имя выходного  файла

output: {
    path: path.resolve(__dirname, 'dist'),
    filename: 'bundle.[contenthash].js'
  },


--- [contenthash] - считает хэш от содержимого


--- пересобираем вебпаком,

----- смотрим в дисте:

появился файл "dist\bundle.e5da4864ab64c2a8be72.js "

причем там же в дисте у нас и старый main.js лежит  (вебпак по умолчанию так называет выходной файл скрипта, пока у нас не было инструкции)


-- если еще раз пересоберем, то bundle.e5da4864ab64c2a8be72.js не изменится (не добавится новый файл с другим именем), так как мы ничего не поменяли 

но если мы что-то поменяем в коде js компонентов, и пересоберем - то :

- в дисте появился еще один бандл 

dist\bundle.fc487b0cf936129d13e2.js

(можно настроить, чтобы папка дист каждый раз подчищалась, сейчас у нас там просто сваливается все добавляется)


---- теперь у нас задача, чтобы при пересборке вебпаком этот обновленный путь, имя бандла js передавалось в index.html, чтобы не обновлять там руками


тут нам помогут плагины вебпака (это вторая составляющая вебпака после лоадеров)


*вебпак говорит что "плагины решают задачи, которые не смогли решить лоадеры"
лоадеры - выполняют трансформации кода
плагины - решают все остальные проблемы


----------- устанавливаем необходимый плагин, который будет обновлять путь в дереве

"npm install html-webpack-plugin"

-- это плагин с очень богатым функционалом ,

но осн заадча его - принимать от вебпака список тех ресурсов, кот он нагенерил, и прокидывать их внутрь HTML-шаблона

-- теперь наш index.html - тоже сам стал исходником

- мы его тоже перемещаем в папку "src"

- мы будем теперь использовать его как шаблон, 

- а результирующий html будет генерироваться плагином 

в "src/index.html"  мы теперь убираем ссылки ан ресурсы

- то есть эту строку убираем 

<script type="module" src="./dist/main.js"></script>

- и добавляем в конфиг инструкцию

сначала нужно его там импортировать

(импортируются плагины в конфиг ЯВНО, в отличие от лоадеров) :


-----

const HtmlWebpackPlugin = require('html-webpack-plugin')


---- и объявляем после module:

  module: {
    rules: [{
      test: /\.js$/,
      use: 'babel-loader',
      exclude: /node_modules/
    }, {
      test: /\.css$/,
      use: ['style-loader', 'css-loader']
    }, {
      test: /\.svg$/,
      type: 'asset/resource'
    }]
  },
  plugins: [new HtmlWebpackPlugin({
    template: './src/index.html'
  })]
}


---- в отличие от лоадеров, ПЛАГИНЫ - это ОБЪЕКТЫ , поэтому мы здесь создаем их с помощью оператора "new"

- и говорим по какому адресу находится шаблон

почистим папку дист и перезапустим сборку

------------ делаем улучшения:


- мы каждый раз записываем в папку дист файлы, это дорогая процедура, 

когда приложение будет большое , это будет заметно что это неоптимально

также папку дист замусоривается неактуальными файлами, если ее не чистить.

- можно для этого найти какой-то плагин чтобы очищал, 

НО есть гораздо более лаконичное решение

 - webpack dev server

---- устанавливаем:

npm install webpack-dev-server


----- у него нет собственной команды для запуска - он прокачивает функционал команды вебпак


--- запускаем

npx webpack serve     


---------- и он запускает нам локальный сервер с нашим приложением:

<i> [webpack-dev-server] Project is running at:
<i> [webpack-dev-server] Loopback: http://localhost:8080/, http://[::1]:8080/
<i> [webpack-dev-server] On Your Network (IPv4): http://10.103.64.26:8080/
<i> [webpack-dev-server] On Your Network (IPv6): http://[fdde:d6cf:b36e::119]:8080/


----------------------

(по внешним таким адресам можно зайти с любого устройства в той же домашней вай фай сети)



-----------   ФИШКА этого  webpack-dev-server  :

- в том что он ничего НЕ сохраняет в нашу файловую систему

- он все ресурсы хранит во внутренней памяти

- он так же при изменениях в коде перезапускает сборку,

- и он умеет модули заменять налету (без перезагрузки страницы - но про это надо отдельно гуглить)

----------

также у webpack-dev-server  есть собственный ключ для своих настроек в конфиге вебпака:

например можно задать, чтобы при запуске дев сервера сразу же запускался браузер

  devServer: {
    open: true
  }
