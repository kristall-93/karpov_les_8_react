----------- теперь у нас есть ДВЕ команды:


1) npx webpack

- она соберет нам бандл и положит внутрь папки 
- она полезна чтобы уже собрать готовый проект

2)  npx webpack serve

- полезна когда разрабатываем


------------

и хоть мы и в курсе что эти команды есть (мы как создатели инфраструктуры)
- НО разработчики кот придут в проект - не знаю на чем написан проект, 
как он собирается, должен ли он собираться, есть ли дев режим, 




-----------------     тут есть 2 способа облегчить им жизнь:



1) редми файл readme.md - он уже есть в проекте

можно в нем рассказать какие команды выполнять



2) НО преподу нравится подход, кот использует возможности npm-скриптов кастомных

----- как она работает:

мы прямо в package.json пишем новую сущность добавляем:

"scripts": {},

- и здесь мы можем указать абсолютно любой ключ, например "dev" -  и указать, какую команду нужно выполнить, когда в терминале запускаем 

"npm run dev"

будет так:


"scripts": {
    "dev": "npx webpack serve"
  },


- тогда приходя в новый проект, можно даже редми не читать, а сразу заходить  в package.json проекта и ищем там "scripts" 
- и там всегда можно понять , какая команда для чего существует

чаще всего используют наименования ключей такие - "start" и "build" :

и тут можно уже в команде "npx webpack serve" опускать "npx" , 
так как NPM сам поймет, что нужно выполнять терминальные команды (беря утилиты из node_modules проекта) :


"scripts": {
    "start": "webpack serve",
    "build": "webpack"
  },

---

И вот уже разработчикам не нужно знать ни про какие вебпаки, 

--- А  теперь можно запускать через "npm run" по ключам из "scripts":

для разработки 

"npm run start"

для билда

"npm run build"



------------------------------------   последний штрих кот нам остался - ДИНАМИЧЕСКИЙ   "mode" , 

- кот должен меняться в зависимости от того, какую команду мы вызвали

- когда мы вызываем дистрибутив для релиза уже , 
чтобы пользователи на него посмотрели  

== мы хотим чтобы  "mode"  был "production"
- потому что как видели ранее, такой режим настраивает вебпак автоматически так, чтобы собирался максимально производительный билд


---- А ДЛЯ  разработки -  mode: 'development'  -
-  нам нужна максимально быстрая скорость разработки, поэтому пофиг на производительность кода в этот момент, а нужна быстрая скорость сборки-пересборки



--------- поэтому здесь нам нужно воспользоваться "переменными окружения Ноды",

кот передаются таким способом:

NODE_ENV=development 

- в  package.json  перед командой "webpack serve"

  "scripts": {
    "start": "NODE_ENV=development webpack serve",
    "build": "webpack"
  },


(webpack.config.js ? ) -  это обычный js модуль, кот запускается внутри Node JS, 
поэтому мы можем эту переменную прочиать в webpack.config.js с помощью 

process.env.NODE_ENV



- в конфиге вебпака сделаем так:

module.exports = {
  mode: process.env.NODE_ENV || 'production',


- так мы обезопасим пользователя - по умолчанию будет вебпак собирать в режиме 'production' всегда, если не указан конкретный NODE_ENV.




---- далее




------- раньше мы писали тот код, кот сразу попадал на наш Gitlab PAGES

при пуше, если мы посмотрим на наш .gitlab-ci.yml  :

----

pages:
  stage: deploy
  script:
    - mkdir .public
    - cp -r * .public
    - mv .public public
  artifacts:
    paths:
      - public
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH

----------------------


при пуше - что тут делаем - это создаем директторию "public"

и выплевываем ее в качестве ратефакта

и "Gitlab Pages" смотрит на содержимое этой папки 

---- сейчас ситуация в нашем проекте сильно изменилась:

перед тем как наш код попадет  , он должен быть СОБРАН



---- препод выступает за то, чтобы это делали не мы руками локально, - 

- нам нужно учить наш CI собирать наше приложение ПЕРЕД тем как оно попадет на "Gitlab Pages"

(тему CI будет разбирать далее подробно)



1) первое что нам нужно сообщить CI, - это то что нам для сборки приложения нужна Нода

пишем образ:

-------------

image: node:20.19.0

------------- 

(посмотрела версию чеерез "node -v")

очень важно сообщать тут версию Ноды, так как в проттивном случае он может использоваь последнюю, а у нас в проекте например не последняя

- и тогда сборка будет отличаться  - в CI будет собираться одним способом, в у нас локально - другим

- это может приводить к проблемам, вам будет сложно дебагить,


--- теперь нам нужно прокачать наш скрипт Pages:

2) перед тем как собирать скрипт, нужно установить зависимости: 

before script: npm install


3) в script будет:

    - npm run build
    - cp -r dist .public




================    ИТОГО, новый вид .gitlab-ci.yml :

----------

image: node:20.19.0

pages:
  stage: deploy
  before script: npm install
  script:
    - npm run build
    - cp -r dist .public
  artifacts:
    paths:
      - public
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
